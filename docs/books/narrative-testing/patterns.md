# Приёмы и структуры

Все примеры ink скомпилированы inkjs (`Compiler`). Сокращения источников — как в principles.md.

---

### PAT-01. Эталонный транскрипт до сценария (golden transcript — «транскрипт-эталон»)
- **Когда применять:** перед первой главой новой истории и перед каждой главой, в которой больше двух развилок. **Когда нет:** короткая правка реплик внутри готовой сцены.
- **Схема:**
  1. Напиши главу так, как её увидит игрок на одном маршруте: время, чат, реплики, нажатые кнопки.
  2. Отметь на полях `[цель]`, `[ставка]`, `[крючок]` — строку, где каждая из них появляется впервые.
  3. Перенеси в ink. Ветки — это отклонения от эталона.
  4. Прогони основной маршрут в игре и сверь с эталоном.
- **На ink:**
```ink
# contact: mira, Мира, teal
// эталонный транскрипт главы 1: каждая строка — то, что игрок должен увидеть
// [цель] игрок понимает задачу; [ставка] понимает, что будет, если не сделать
-> ch1
=== ch1 ===
День 1 · Ключи #from:mira #sys:mira #chapter
ты взял мои ключи? #from:mira #delay:5s
от гаража. серые #delay:4s
* [Нет. А что? #to:mira]
* [Может, и взял #to:mira]
- в гараже машина отца #from:mira #delay:20s
в восемь её забирает полиция
// [ставка] появилась на 7-й строке
* [Я поищу #to:mira]
    -> END
* [Промолчать #to:mira #silent]
    ты тут? #from:mira #delay:10m
    -> END
```
- **Цена:** глава пишется полтора раза, но эталон потом служит регрессионным тестом (P-16).
- **Ловушки:** если писать эталон только по «хорошему» маршруту, «Промолчать» и отказы останутся без проверки. Нужен второй эталон для маршрута «молчун».
- **Источник:** [ifMUD] — участник Roger сравнивает разработку через тесты (TDD) с тем, чтобы сначала написать транскрипт. Разметка `[цель]/[ставка]/[крючок]` — знание модели, уверенность: средняя.

### PAT-02. Волны тестеров (staged beta — «бета волнами»)
- **Когда применять:** любая история длиннее одной главы. **Когда нет:** правка одной реплики. Её проверяет бот и сам автор.
- **Схема:**
```
скелет → чтение вслух (2 чел.) → правка
       → волна 1: 2–3 быстрых тестера, главы 1–2 → правка
       → волна 2: новые 3–5, вся история, реальное время → правка
       → волна 3: тестеры волны 1 только по списку изменений
```
- **На ink:** в сборке для волны 1 конец ставится после последней готовой главы, чтобы тестер знал, где остановиться.
```ink
# contact: mira, Мира, teal
-> ch1
=== ch1 ===
День 1 · Ключи #from:mira #sys:mira #chapter
ты взял мои ключи? #from:mira
* [Нет #to:mira]
- -> beta_stop
// временная заглушка: дальше глава 2 не готова
=== beta_stop ===
Конец тестовой части. Спасибо! #sys
-> END
```
- **Цена:** 3 раунда — это 1–3 недели при реальном времени. Каждая волна требует сводки (P-05, P-06).
- **Ловушки:** если не убрать заглушку из релиза, `check:story` покажет её как финал. Нужно проверять, что финала «Конец тестовой части» нет в списке.
- **Источник:** [Short] — повторный тест после фиксов и конец после последней решаемой загадки в пре-бете; [CoG-all] — один автор начинает примерно с 10 быстрых тестеров и расширяет круг постепенно. Число волн и размеры групп — наше предложение.

### PAT-03. Вход в середину с набранным состоянием (save files for branches — «сохранения на развилках»)
- **Когда применять:** нужно протестировать главу 8 при `owen_turned = true`, не проходя 7 дней. **Когда нет:** тест первого впечатления. Там прыжки запрещены.
- **Схема:** тестовый узел → выставить переменные, как после типичного маршрута → прыгнуть в главу. Отладочная шторка уже умеет прыгать к узлу и переключать переменные. Тестовый узел фиксирует набор переменных, чтобы его можно было повторить.
- **На ink:**
```ink
# contact: mira, Мира, teal
VAR mira_trust = 0
VAR keys_found = false
-> ch1
// вход для тестеров: прыжок в главу 2 с уже набранным состоянием
=== test_ch2_trusting ===
~ mira_trust = 3
~ keys_found = true
-> ch2
=== ch1 ===
День 1 · Ключи #from:mira #sys:mira #chapter
ты взял мои ключи? #from:mira
* [Да. Вот они #to:mira]
    ~ keys_found = true
    ~ mira_trust += 1
* [Нет #to:mira]
- -> ch2
=== ch2 ===
День 2 · Гараж #from:mira #sys:mira #chapter
{keys_found:
    я открыла гараж #from:mira #delay:1h
- else:
    гараж так и закрыт #from:mira #delay:1h
}
{mira_trust >= 3: тебе одной скажу #from:mira}
-> END
```
- **Цена:** 1 узел на мир или персону. В «Чужом голосе» нужно три — по числу значений `world`.
- **Ловушки:** `check:story` пометит `test_*` как недостижимые узлы. Бот должен пропускать префикс `test_`. Состояние должно быть таким, которое реально набирается: значения стоит сверять с медианой по прогонам бота.
- **Источник:** [ifMUD] — zarf о раздаче сохранений на крупных развилках; спор о прыжках: для теста впечатления они вредят, для поздних глав полезны.

### PAT-04. Боты с характером (persona bots — «персоны»)
- **Когда применять:** всегда вместе со случайным ботом, если есть `#silent`, отказы или проверки доверия. **Когда нет:** линейный пролог без выборов.
- **Схема:** у каждого бота своё правило выбора, доли финалов считаются отдельно:
```
random       — равновероятно
silent       — #silent, если есть, иначе первая кнопка
talker       — случайная, но никогда не #silent
loyal        — кнопка, после которой растёт *_trust, иначе случайная
suspicious   — кнопка с «?» в тексте, иначе случайная
first / last — всегда первая / последняя (ловит «правильную» первую кнопку)
```
- **На ink:** боту нужно, чтобы сами кнопки выдавали свой характер. `#silent` видно по тегу. Чтобы бот узнал «доверчивую» кнопку, её последствие должно стоять сразу под ней, в первой строке.
```ink
# contact: mira, Мира, teal
VAR mira_trust = 0
-> ask
=== ask ===
это ты взял ключи? #from:mira
* [Нет. Честно #to:mira]
    ~ mira_trust += 1
* [А ты докажи #to:mira]
    ~ mira_trust -= 1
* [Промолчать #to:mira #silent]
- {mira_trust > 0: ладно. верю #from:mira}
{mira_trust < 0: понятно #from:mira}
-> END
```
- **Цена:** около 40 строк в `check-story.mjs`, ink не меняется.
- **Ловушки:** «loyal» узнаёт кнопку, только заглянув на шаг вперёд (клон состояния и `ChooseChoiceIndex`). Без этого он угадывает. Доли у разных ботов — не прогноз поведения людей, а разброс: насколько финал зависит от стиля игры.
- **Источник:** [ifMUD] — Short о несовпадении автотеста и людей. Набор персон — знание модели, уверенность: средняя.

### PAT-05. Эхо выбора (choice acknowledgement — «отклик на выбор»)
- **Когда применять:** кнопки, которые сходятся сразу (в «Чужом голосе» таких 126 из 338). **Когда нет:** намеренно пустые реплики-ритм вроде «Ладно», если вокруг них много значимых выборов.
- **Схема:** выбор → немедленная реакция, отличная по смыслу → схождение → **ещё одно упоминание позже** через переменную.
- **На ink:**
```ink
# contact: mira, Мира, teal
VAR tone = ""
-> ask
=== ask ===
ты правда видел его машину? #from:mira #delay:5s
* [Видел. В 23:10 у моста #to:mira]
    ~ tone = "sure"
    23:10. запомнила #from:mira #delay:30s
* [Кажется, видел #to:mira]
    ~ tone = "unsure"
    кажется — это не видел #from:mira #delay:40s
* [Промолчать #to:mira #silent]
    ~ tone = "silent"
    ладно. потом #from:mira #delay:15m
- скину это следователю #from:mira #delay:20s
{tone == "sure": скажу, что ты уверен}
{tone == "unsure": скажу, что ты не уверен. так честнее}
{tone == "silent": про тебя ничего не скажу}
-> END
```
- **Цена:** 1–2 строки на кнопку и одна переменная на развилку.
- **Ловушки:** эхо, которое просто пересказывает выбор («ты сказал, что видел»), считывается как автоответчик. Эхо должно сообщать что-то новое: что персонаж сделает с ответом.
- **Источник:** знание модели (жалобы тестеров на «рельсы» и выборы без последствий), уверенность: средняя; [CoG-all] — тестеры проверяют «railroading» и качество выборов.

### PAT-06. Отложенное последствие с эхом по дороге
- **Когда применять:** переменная меняется в главе N, а читается только в финале (84 кнопки «Чужого голоса» меняют только переменные). **Когда нет:** счётчик, который сознательно скрыт и раскрывается в финале. Тогда в финале нужно явное «потому что ты…».
- **Схема:** `~ x = true` в главе N → эхо в главе N+1 (реплика, которая без выбора не появилась бы) → использование в финале.
- **На ink:**
```ink
# contact: mira, Мира, teal
# contact: oleg, Олег, orange
VAR told_oleg = false
-> ch1
=== ch1 ===
День 1 #from:mira #sys:mira #chapter
олег спрашивает, где я была ночью #from:mira
* [Сказать Олегу, что она была дома #to:oleg #label:Прикрыть Миру]
    она была дома. всю ночь #me:oleg
    ~ told_oleg = true
* [Не вмешиваться #to:mira #silent]
- -> ch2
=== ch2 ===
День 2 #from:mira #sys:mira #chapter
// эхо через главу: последствие видно до финала
{told_oleg:
    олег сегодня со мной не здоровается #from:mira #delay:2h
    что ты ему сказал?
- else:
    олег спрашивал ещё раз. я соврала сама #from:mira #delay:2h
}
-> END
```
- **Цена:** по 2–4 строки на каждую значимую переменную.
- **Ловушки:** эхо попадает в ветку, куда половина игроков не заходит. Его надо ставить в общий узел после схождения.
- **Источник:** знание модели, уверенность: средняя. Проверка «переменная записана, но не читается до финала» — наша (for-relayer §2).

### PAT-07. Ловушка-финал → последний шанс
- **Когда применять:** бот показывает, что одна развилка забирает больше трети прохождений в финал до кульминации. Так в «Чужом голосе» работает `ch10_maya`: «Делай, что считаешь нужным» ведёт в `fin_revenge` сразу, «Промолчать» — через `ch10_maya_go`, если нет `tom_hold`, и даже «Подожди» туда же, если `maya_trust < 3`. **Когда нет:** ранний финал задуман как наказание и о нём заранее предупредили.
- **Схема:**
```
развилка ──(ошибка)──> предупреждение: «стою у дома. ещё минута» ──┬─> кульминация
                                                                  └─> ранний финал
```
- **На ink:**
```ink
# contact: dana, Дана, red
# contact: mira, Мира, teal
VAR dana_trust = 0
-> dana_door
// было: два ответа из трёх сразу вели в финал «месть» до кульминации
=== dana_door ===
в семь я выкладываю её имя #from:dana #delay:15m
* [Подожди. Она скажет сама #to:dana]
    {dana_trust >= 2: -> climax}
    она два года молчала #from:dana #delay:3m
    -> dana_last
* [Делай, что считаешь нужным #to:dana]
    -> dana_last
* [Промолчать #to:dana #silent]
    -> dana_last
=== dana_last ===
// второй шанс: финал остаётся, но игрок видит, куда идёт
стою у её дома. ещё минута #from:dana #delay:20m
* [Не надо. Я буду там через час #to:dana]
    -> climax
* [Выкладывай #to:dana]
    -> fin_revenge
=== climax ===
она открыла дверь #from:mira #delay:40s
-> END
=== fin_revenge ===
пост ушёл #from:dana #delay:1h
-> END
```
- **Цена:** один узел и 2–3 строки на ловушку.
- **Ловушки:** если «последний шанс» срабатывает всегда, ранний финал исчезает и выбор обесценивается. Шанс должен стоить чего-то: другой кнопки, раскрытия, потерянного доверия.
- **Источник:** наш приём. Он сохраняет схождение к кульминации, как в структуре branch and bottleneck (ветвление с бутылочным горлышком, термин Sam Kabo Ashwell; знание модели, уверенность: высокая). Диагностика долей — [CoG-auto].

### PAT-08. Пустая ветка хаба → отказ с уликой
- **Когда применять:** кнопка в хабе ведёт в узел, где 0–1 строка и возврат в хаб. Так в «Чужом голосе» работают `ch1_beth` («Бет не в сети») и почти пустой `ch1_kt`. **Когда нет:** тишина и есть ответ, и позже персонаж её объясняет. Тогда объяснение должно стоять в той же главе.
- **Схема:** кнопка → `Прочитано` → пауза → короткий отказ, в котором есть факт → флаг → хаб.
- **На ink:**
```ink
# contact: beth, Бет, purple
# contact: mira, Мира, teal
VAR beth_hint = false
-> hub
=== hub ===
* [Здравствуйте, я из опроса #to:beth #label:Написать Бет]
    -> beth
* [Хватит. Подождать Миру #to:mira #silent]
    -> END
=== beth ===
// было: «Бет не в сети» и назад в хаб. Стало: отказ, который несёт улику
Прочитано #sys:beth #delay:2m
не пиши мне про карьер #from:beth #delay:6m
я уже всё сказала тому полицейскому
~ beth_hint = true
-> hub
```
- **Цена:** 2–3 строки на ветку.
- **Ловушки:** у каждого отказа должна быть своя улика. Три одинаковых «не пиши мне» в одном хабе читаются как заглушки.
- **Источник:** [Ryan] — «missing dialogue» (пропущенные реплики) как отдельный класс ошибок; наше переложение.

### PAT-09. Бумажный прогон на два голоса (paper read-through — «читка»)
- **Когда применять:** скелет готов, прозы нет; или глава переписана целиком. **Когда нет:** проверка пауз и уведомлений. На бумаге их не почувствовать (P-17).
- **Схема:** один человек читает реплики всех контактов и держит паузы словами («проходит два часа»). Второй выбирает вслух и говорит, что думает (think-aloud — «рассуждение вслух»). Автор молчит и записывает: где игрок спросил «кто это?», где выбрал не то, что ждали, где заскучал.
- **На ink:**
```ink
# contact: mira, Мира, teal
// бумажный скелет: одна строка на сцену, проза потом
// вслух читают двое: один за всех контактов, второй выбирает
-> s1
=== s1 ===
СЦЕНА 1: Мира просит найти ключи. Цель ясна к 3-й строке #from:mira #chapter
* [ВЫБОР: помочь #to:mira]
    -> s2
* [ВЫБОР: отказать #to:mira]
    -> s2_refuse
=== s2_refuse ===
СЦЕНА 2б: Мира присылает фото гаража. Отказ не принят, но замечен #from:mira
-> s2
=== s2 ===
СЦЕНА 3: в гараже нет машины. Крючок главы #from:mira #delay:2h
-> END
```
- **Цена:** 30–60 минут на главу, без кода.
- **Ловушки:** читающий, который знает сюжет, подсказывает интонацией. Лучше, чтобы читал не автор. «Игрок» не должен видеть скелет целиком.
- **Источник:** think-aloud и бумажное прототипирование — знание модели, уверенность: высокая (стандартные методы UX). Идея проверять сюжет до играбельной версии — [Dankoff] по аннотации.

### PAT-10. Проверка пересказом (retell check)
- **Когда применять:** после главы 1 и после каждой главы с раскрытием. **Когда нет:** во время игры. Вопрос посреди главы сбивает погружение.
- **Схема:** тестер своими словами отвечает на три вопроса: «что случилось?», «кто что хочет?», «что, по-твоему, будет дальше?». Ответ сверяется с картой фактов, которые автор считает установленными к этому моменту. Расхождение означает «непонятно» (RED-07). Пустой третий ответ означает, что крючка нет (RED-05).
- **На ink:** автор помечает установленные факты комментарием, чтобы было с чем сверять пересказ:
```ink
# contact: mira, Мира, teal
-> ch1
=== ch1 ===
День 1 #from:mira #sys:mira #chapter
// ФАКТ-1: машина отца в гараже
в гараже машина отца #from:mira
// ФАКТ-2: в восемь её заберут
в восемь её забирает полиция #delay:10s
// КРЮЧОК: почему полиция, если отец «в отъезде»?
он же в отъезде. уже месяц #delay:30s
-> END
```
- **Цена:** 5 минут тестера на главу. Комментарии `// ФАКТ-` в ink игроку не видны.
- **Ловушки:** вопрос «ты понял, что…?» подсказывает ответ. Спрашивай открыто.
- **Источник:** знание модели (проверка понимания в user research), уверенность: средняя. Пункты PTC «трудно понять, что происходит» и «персонажи неясны» — родственная шкальная версия.

## Устройство систем источника

В подборке пять систем: цикл беты по Short, ранний групповой разбор Ubisoft, автотесты CoG, шесть категорий нарративного QA у Ryan и анкета PTC. Для каждой — элементы, вход и выход шагов, что ломается без шага, где её понимают неправильно, как ужать для короткой формы. Пересказ свой, порядок шагов — по источнику.

### SYS-01. Цикл беты (Short, IFWiki, форумы CoG)
| шаг | вход → выход | если пропустить |
|---|---|---|
| 1. Готовность | сборка проходима до конца или с заглушкой после последнего готового места → сборка, в которой тестер не упрётся в недописанное | тестер тратит отзыв на то, что автор и так знает (P-03) |
| 2. Бриф | список известных багов, 1–3 вопроса, договорённость о пометках → записка тестеру | пометки в разном формате, сводку не собрать |
| 3. Игра с транскриптом | сборка + записка → полная запись с пометками по ходу | остаётся пересказ по памяти, редкий баг не воспроизвести (P-04, LESSON-01) |
| 4. Сводка | транскрипты → список «место · симптом · кто ещё» | спор о решениях вместо симптомов (P-05) |
| 5. Правка и регрессия | сводка → правки + маршрут на каждый баг | исправления ломают соседние ветки (P-16) |
| 6. Следующий раунд | список изменений + свежие люди → проверенные правки, новое первое впечатление | второй раунд проверяет только фиксы, начало никто не видит заново (P-08) |

- **Как понимают неправильно:** «бета» = проверка опечаток. IFWiki прямо называет бету проверкой удобства, которая заодно показывает, что игрокам нравится (https://www.ifwiki.org/Betatesting). Альфа идёт раньше, пока сюжет не закончен. Вторая ошибка — один большой раунд в конце. Short советует отдавать игру тестерам за месяц или больше до срока, чтобы осталось время исправить найденное (https://emshort.blog/2009/05/17/in-praise-of-the-glorious-practice-of-beta-testing/). Что правки порождают новые баги и нужен повторный раунд — наш вывод (P-16).
- **У CoG устроено так:** тестеров пускают партиями, бета идёт обычно 3–4 недели. Отзывы идут через редактора, и он может не всё передать автору. После закрытия беты идёт корректура, и от тестеров ждут только бесспорные баги и нестыковки (FAQ форума, https://forum.choiceofgames.com/t/beta-testing-faqs-please-read-before-applying/131673).
- **Короткая форма:** шаги 2–4 сжимаются в одну строку брифа и два вопроса после игры. Шаг 6 обязателен всегда, но достаточно одного свежего человека на начало.

### SYS-02. Ранний групповой разбор сюжета (Narrative Review Process, Ubisoft Montreal)
По пересказу доклада Dankoff на GDC 2015 (https://www.gamedeveloper.com/audio/gdc-2015-the-delayed-impressions-of-a-games-user-researcher) и аннотации статьи ICIDS 2015. Конкретных вопросов анкеты и метрик в открытых материалах нет.
| шаг | вход → выход | если пропустить |
|---|---|---|
| 1. Группа | 6–10 человек: примерно половина сценаристов, половина других разработчиков проекта → состав разбора | одни сценаристы находят ремесленные огрехи, но не то, чего не поймёт посторонний |
| 2. Материал | очень ранний набросок сюжетного бита → текст для заметок | разбор готовых сцен приходит тогда, когда менять уже поздно (исходная проблема метода) |
| 3. Заметки | каждый пишет отдельно → набор заметок | громкий участник задаёт мнение группы |
| 4. Сведение | заметки → отчёт исследователя | сценарист получает сырой поток и защищается |
| 5. Разговор один на один | отчёт → сценарист понимает, что нашли | группа обсуждает сценариста, а не текст |
| 6. Групповое обсуждение | отчёт + сценарист → решения | проблемы найдены, но не решены |

- **Заявленный эффект:** сценаристы находили неизвестные им проблемы и получали помощь с известными. Росли согласие команды и число ранних итераций. Автор пересказа сам оговаривает, что успех не доказан: игры ещё не вышли (LESSON-09).
- **Как понимают неправильно:** как замену плейтесту. Метод проверяет набросок глазами коллег, а не игроков. Понятность для постороннего проверяют позже (SYS-05).
- **Короткая форма для relayer:** 3–4 человека, из них 1–2 не пишут истории. Материал — скелет главы в 10–15 строк (PAT-09). Каждый пишет 3 заметки молча, автор сводит их сам, потом 15 минут обсуждения только о решениях. Чек-лист — checklists §5.

### SYS-03. Автотесты CoG: quicktest и randomtest
- **Элементы:** quicktest проверяет, что любой вариант синтаксически проходим. randomtest делает тысячи случайных прохождений и считает попадания в каждую строку. Порог редкости: около 1 % — «очень трудно», около 0,1 % — «исключительно трудно» (P-12). Ориентир доли текста за прохождение — 20 %, нижняя граница — 10 % (P-13).
- **Вход → выход:** игра → счётчики строк и список ошибок. Счётчики → решение: упростить ветку, отметить её наградой или оставить.
- **Если пропустить:** редкие ветки и мёртвый текст видны только по жалобам после выхода.
- **Как понимают неправильно:** считают долю бота долей игроков. Сам CoG показывает обратное: петля подтверждения поднимает долю «сдаться» с ~25 % до ~40 %, и это чистая арифметика (LESSON-03). Ходы, которых человек не сделает (ввод текста, отмена подтверждения), из случайного прогона нужно убрать.
- **Короткая форма:** у нас это `check:story`. Добавить: персоны (PAT-04) и пометку узлов-петель, чтобы бот не перевзвешивал их.

### SYS-04. Шесть категорий нарративного QA (Ryan)
Категории перечислены в P-14. Порядок прохода, который следует из логики Ryan (QA получает бриф, затем ищет в своей зоне), — наш вывод:
1. Бриф: что считается каноном (характеры, правила имён, хронология) → эталон для сверки. Без него «сбой голоса» — вкусовщина.
2. Факты и хронология → список расхождений.
3. Голос → строки, которые выбиваются.
4. Логика → кто знает то, чего ему не сообщали.
5. Пропущенные реплики → кнопки без ответа.
6. Имена → формы по говорящим.
7. Орфография → последний шаг, потому что правки 2–6 вносят новые опечатки.
- **Как понимают неправильно:** QA сюжета путают с вычиткой. Вычитка — только шаг 7, а шаги 2–5 ловят то, чего корректор не видит.
- **Короткая форма:** шаги 2–6 свести в одно чтение «по контактам». Все реплики одного `#from` подряд показывают голос, имена и логику сразу. Это 10 минут на историю в 5 минут.

### SYS-05. Анкета и проверка понимания (PTC, Bromley)
- **Элементы PTC:** семь шкальных пунктов. Нам нужны те, что о понятности, внимании и сопереживании, а пункты о читаемости и звуке мы выкинули (checklists §4). PTC оговаривает, что пункты не валидированы (P-15).
- **Проверка понимания у Bromley (Games User Research):** прототип — слайд на бит сюжета. Сессия один на один. После каждого бита — три вопроса: что сейчас происходит, почему, чего ждёшь дальше. Не спрашивать «понятно ли?» и не просить идей сюжета. Повторять на каждом этапе готовности, но всякий раз с новыми людьми: кто видел историю, второй раз не годится (https://gamesuserresearch.com/how-to-playtest-your-games-story/). Интерес меряют отдельно, в групповых сессиях: регулярно спрашивают, насколько интересно, что будет дальше, и строят по ответам кривую спада.
- **Вход → выход:** бит → три ответа → расхождение с замыслом автора → тип поломки (непонятно / нет крючка).
- **Если пропустить «почему»:** игрок пересказывает события верно, но мотивации не видит, и потом «не верит» поступкам.
- **Как понимают неправильно:** вопрос «понятно?» вместо открытых вопросов. Игрок отвечает «да», даже когда придумал своё объяснение (P-09).
- **Короткая форма:** наш PAT-10 — та же тройка вопросов, но после главы, а не после бита. Для истории на 5 минут — один раз в конце и один раз после первой паузы ≥1 ч.

## Нюансы к паттернам

- **PAT-01 (эталон).** На 5 сообщениях эталон — это сама сцена, и отдельный файл не нужен. На 50 и больше он окупается только с маршрутом «молчун». CoG советует не начинать с первой главы (choiceofgames-design:P-16). Компромисс: эталон пишется первым для главы середины, а для главы 1 — после неё (for-relayer §6).
- **PAT-04 (персоны).** Персоны искажают доли так же, как петли у CoG (LESSON-03). Если после `#silent` идёт повтор «ты тут?» с той же кнопкой «Промолчать», `silent` проходит петлю до конца, а человек, скорее всего, на повторный вопрос ответит (наша оценка). Проверь, сколько из 100 % `revenge` у `silent` приходится на такие петли. Мы это не считали, это гипотеза.
- **PAT-05 (эхо).** Не работает, если между кнопкой и эхом прошла пауза ≥1 ч: игрок уже не помнит, что нажимал. Тогда эхо называет поступок («ты же сказал, что уверен»), хотя в обычном случае такой пересказ запрещён. Для 5-сообщенной сцены достаточно немедленной реакции, отложенное эхо не нужно.
- **PAT-07 (последний шанс).** Добавляет петлю: доля раннего финала у случайного бота упадёт сама собой. Сравнивай по `talker` и `loyal` (LESSON-03). Если ранний финал задуман как частый, порог RED-12 к нему не применяется, нужна только пометка автора.
- **PAT-08 (отказ с уликой).** На 5 сообщениях хаба нет, отказ — это одна реплика. В хабе из 5+ кнопок одна намеренно пустая ветка допустима, если её пустота объяснена позже (как `ch2_beth`).
- **PAT-09 (читка).** Для группы — SYS-02, для одного свежего игрока — SYS-05. Не смешивай: участник группового разбора уже не «свежий».
- **PAT-10 (пересказ).** По Bromley, «почему» — отдельный вопрос, без него пересказ проверяет только события. Добавь его: «почему Мира просит тебя, а не полицию?».

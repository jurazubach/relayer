# Критика плана: знания → скиллы → агенты

Предмет — `docs/playbook/build-plan.md` (дальше «план»). Сверено с `skills.md`, `rules.md`, `checks.md`,
`story-findings.md`, `REVIEW.md`, `CLAUDE.md`, `docs/capabilities.json`, `src/engine/engine.ts`, тремя
историями и папками `attention-today`, `narrative-testing`, `chat-fiction-apps`, `mystery-fair-play`.
Факты о репозитории проверены чтением файлов и прогоном `npm run check:story` и `npm run graph`
24.10.2026. Оценки стоимости и устройства Claude Code — мои рассуждения, их надо подтвердить в T-00.

## Главное (самое важное сверху)

1. **Эксперимент Э2 устроен как проверка памяти, а не диагностики.** Скилл `story-review` берёт в знания
   `story-findings.md` «как эталон» (строка 115 плана, в `skills.md` S-10 — «чтобы не находить заново
   уже известное»). `story-opening` держит `cases.md` с разбором начал трёх историй. Все references
   по контракту содержат «антипримеры из наших историй, с именами узлов». Потом Э2 считает, сколько
   находок из топ-10 скилл нашёл на тех же историях. Ответы лежат внутри скилла, а эталон писала та же
   модель. Получится 10 из 10, и это ничего не скажет о новой истории. **Вместо этого:** отложенная
   выборка (калибровка на двух историях, проверка на третьей, без её антипримеров в references),
   мутационный тест (в чистую копию вносятся известные дефекты) и точность по отметкам автора
   (принял / отклонил находку).
2. **Проверки `C-01…C-54` никто не реализует.** В фазе 0 есть `story:trace/vars/sessions/cast`, но
   нет задачи «написать проверки». Вместо этого счёт разбросан по скиллам: `pace.mjs`, `choices.mjs`,
   `endings.mjs`, `clues.mjs`, `chapter-lint.mjs`, `plan-check.mjs`. При этом `checks.md` написан как
   спецификация для `check-story.mjs` и `story-graph.mjs`. Получатся пять частичных линтеров с
   собственными порогами. T-04 при этом требует прогнать «первую волну проверок» до того, как их
   кто-то написал. **Вместо этого:** одна команда `story:lint` по ID проверок, пороги в одном
   машиночитаемом `thresholds.json`, скилл фильтрует вывод по своим `C-NN`.
3. **Пороги будут жить в четвёртой копии.** `REVIEW.md` уже сводил около 25 расхождений порогов
   между `rules.md`, `checks.md` и `skills.md`. План добавляет `references/thresholds.md`, `load.md` и
   «правила и пороги с их ID» в каждом reference. Это 13 скиллов по 4–5 файлов, около 60 новых мест,
   где число может разойтись. **Вместо этого:** число записано только в `thresholds.json`. References
   ссылаются на `C-NN` и не повторяют число, команда печатает порог рядом с замером. Отдельный линт
   ищет в `.claude/skills/**` цифры рядом с `C-`/`R-` и роняет сборку.
4. **Вложенная оркестрация в Claude Code не работает так, как нарисовано.** По моему знанию
   (проверить в T-00), субагент не может запускать субагентов. Отсюда три поломки:
   - `story-auditor` «вызывает `story-review`», а `story-review` «запускает аудиторов» (строки 115 и 143) —
     это цикл;
   - `chapter-writer` и `story-architect` берут `story-opening`, а тот опирается на холодного читателя —
     агент внутри агента;
   - `story-fixer` «после правки — тот же аудитор-скилл» — то же самое.

   **Вместо этого:** оркестрация только в главной сессии через скиллы, агенты — листья без права
   вызывать других агентов.
5. **Автоподхват под угрозой ещё до первого своего скилла.** В текущей сессии у пользователя около 150
   скиллов плагинов (cockroachdb, brightdata, engineering, anthropic-skills…), и у многих уже показано
   только имя без описания: бюджет листинга исчерпан. Ещё 13 скиллов и 6 агентов с похожими фразами
   («проверь темп» есть и у `story-pace`, и у `story-auditor`) сработают ненадёжно. **Вместо этого:**
   - выключить нерелевантные плагины на уровне проекта;
   - таблица «симптом → скилл» в `CLAUDE.md` — она загружена всегда, в отличие от описаний;
   - у агентов нет пользовательских фраз: их вызывают только скиллы;
   - тест срабатывания (фразы «да / нет») гонять с первой волны, а не только в Э5.
6. **Сценарий нельзя удобно править: ink — одна экранированная строка JSON.** `the-number.json` — 86
   строк файла на 41 тыс. знаков ink, весь ink в одной строке с `\n`. Агенты будут писать и править
   главы через Edit по экранированному тексту, номера строк в находках не совпадут ни с чем. План
   этого не видит. **Вместо этого:** в T-01 добавить `story:unpack` / `story:pack`. Исходник —
   `src/stories/<id>/story.ink` плюс `meta.json`, а JSON собирается из них (или ink хранится отдельным
   файлом и подтягивается в сборке). Тогда же номера строк станут стабильными для находок и разметки.
7. **Цель автора «научиться писать» не обслуживается.** Всё в плане — автоматизация: найти, починить,
   сгенерировать. `skills.md` §7 прямо выбрасывает `/cover` как «упражнение для обучения автора».
   **Вместо этого:**
   - режим «объясни» в каждом отчёте: почему это плохо, ссылка на источник, как сделать самому;
   - скилл `story-kb` превратить в наставника: разбор своей сцены и упражнения;
   - правки по умолчанию — предложение с вариантами, а не применённый патч.
8. **Продуктовые дыры, которые скиллами не закрыть, план не называет.**
   - **Реальное время против карточки.** У «Чужого голоса» на карточке ≈ 90 минут, а `check:story`
     даёт паузы от 166 до 185 ч (медиана 175 ч 45 мин). У THE NUMBER при 25 минутах — 22–25 ч.
   - **Нет системных пушей** (`attention-today/attention.md`, «Как это выглядит в движке»): игрок
     возвращается через неделю только по памяти.
   - **Сохранение не привязано к версии сценария.** `engine.ts` (`restore`) грузит `storyState` без
     проверки версии истории. После правки ink старые сохранения игроков ломаются или ведут себя
     непредсказуемо, а «перекапывать истории полностью» на `master` значит деплоить это игрокам.

   **Вместо этого:** скилл выпуска (`story-release`) и фича движка «версия сценария в сохранении»
   в реестре.
9. **В фазе 0 потеряны журнал выборов (K-05), финалы по узлам (K-04) и две персоны.** `skills.md`
   ставит их в фундамент, база (`narrative-testing:LESSON-01`) называет журнал главным условием
   полезных отзывов. В плане их нет, и замены нет. Без K-05 `story-playtest digest` не привяжет отзыв
   к узлу. Без персоны `first` нельзя проверить пункт 4 «Не подтвердилось» в `story-findings.md`.
10. **Скилл под главную боль аудитории исчез.** `attention-adapt` (S-11 в `skills.md`) — «игроки
    бросают», «сделай версию на 5 минут». В плане его нет и не сказано, куда он делся. Фразы этой темы
    никуда не маршрутизируются.

## По разделам плана

### 1. Нарезка скиллов

**`story-choices` перегружен — разбить.** Сейчас в нём 37 проверок (C-01…C-19, C-40…C-43), 28 правил
(R-43…R-58 и R-102…R-113), семь приёмов (F-07…F-11, F-14), шесть references и ещё «владелец
структур ветвления». Это три разные работы:
- кнопка и её отклик;
- переменные и эхо;
- финал и его распределитель.

Финалы — отдельная проблема с отдельными фразами («финал случайный», «конец тянется»). Четыре пункта
топ-10 из десяти — про финалы (2, 3, 4, 7). `skills.md` S-08 держал их отдельно.

→ `story-choices` (кнопки, молчание, переменные, эхо: C-01…C-05, C-08…C-19) и `story-endings` (C-06,
C-07, C-40…C-43, F-09, F-10, F-12). Структуры ветвления (`structures.md`) отдать `story-plan`: это
решение проектирования, а не диагноза.

**`story-cast` перегружен — разбить.** Состав и уровни, карточка героя, голос, сведения между чатами,
дуги — пять тем, у которых разные данные и разные фразы. «Голоса сливаются» и «слишком много чатов»
чинятся разными приёмами.

→ `story-cast` (сколько контактов, когда открывать, уровни, хабы, молчащие: C-21, C-45, C-50) +
`story-voice` (голос, лист голоса, слепой тест, **редактура реплик**: C-44, C-46, C-47, C-48, C-14, R-119)
+ `story-continuity` (кто что знает по путям, слияния, хронология, факты, `#rename`: C-49, C-51, F-13).

`story-continuity` — это и «перенос сведений между чатами», и будущий канон вселенной, и проверка после
правок между версиями. Сейчас C-49 и C-51 у разных скиллов или ни у кого, а F-13 вызывается из
`story-review`.

**`story-opening` + `story-pauses` — не объединять.** Общий у них только режим холодного читателя
(`opening` и `return`). Начало — один раз и про понимание мира. Возвращение — каждый раз и про
память. Фразы и приёмы разные (F-04 против F-01…F-03). Общее вынести в протокол `cold-reader`, а не
сливать скиллы.

**`story-core` + `story-plan` — объединить ядро с конвейером создания, план оставить.**
`story-core` в одиночку — 10 строк шапки. Пользователь говорит «придумай историю про…» и ждёт историю,
а не логлайн. Нужен вход создания, который ведёт «идея → ядро → одобрение → план → главы → ревью» с
остановками на одобрение. → `story-new` (бывший `story-core` плюс конвейер). `story-plan` остаётся
отдельным: его зовут и для чужого скелета («собери план», «переделай структуру»).

**`story-pace` против `story-pauses` — пересечения.**
- **C-37** назначен обоим.
- **C-33 «объём сессии»** стоит у `pace`, хотя сессии — это `pauses`.
- **R-25…R-31** назначены и `pace`, и `plan`.
- **R-102…R-113** назначены и `choices`, и `plan`.
- **R-34…R-36** назначены и `cast`, и `plan`.

→ Граница: `pace` — ритм внутри сессии, `pauses` — всё между сессиями (C-26…C-33). У правил один
владелец-диагност, `plan` ссылается на них ID.

**Без владельца:**
- **C-39** (стык глав), **C-47** (маркеры в тексте), **C-49** (факты, хронология, карточка),
  **C-52**, **C-53** — нет ни у одного скилла плана;
- **R-114…R-119** («Чего не делать») отданы только `story-fix`, хотя:
  - R-117 (вымысел) нужен генерации;
  - R-114 и R-115 (этика) нужны аудиту пауз и выпуску.

**Каких не хватает.**

| тема | вердикт | почему |
|---|---|---|
| голоса и диалог | нужен (`story-voice`) | см. выше; сейчас утоплен в `cast` |
| перенос сведений между чатами | нужен (`story-continuity`) | многочатовость — главная особенность формата; F-13 и C-51 без хозяина |
| вселенная и связи историй | **не сейчас как скилл**, но зарезервировать | движок хранит прогресс по `relay:<storyId>`, межисторических флагов в реестре нет. Скилл без фичи движка бесполезен. Нужны поле `// мир:` в шапке, `docs/worlds/<series>/bible.md` и `planned`-фича в реестре |
| карточка и описание для каталога | нужен (`story-release`) | `tagline`, `synopsis`, `features`, `minutes`, `characters` никто не проверяет. Факт: карточка «90 минут» при 7 сутках пауз (`chat-fiction-apps:RED-09`). В `the-number` 6 героев в `characters` и 11 контактов в ink |
| локализация и тон | тон — в `story-voice`, локализация — не сейчас | все истории русские. Но сшитые по условиям реплики (R-119) плохо переводятся — записать как ограничение |
| монетизация и этика удержания | нужен как часть `story-release` + сквозной гейт | `dark-patterns.md` спрятан в `story-pauses`. Где стоит платная граница (только на стыке глав, первая глава — бесплатная демонстрация), «платный выбор и вина за бесплатный» (`chat-fiction-apps` lessons) — это решение выпуска, а не пауз |
| генерация из короткой идеи | нужен вход (`story-new`) | у `story-architect` выход — план; кто пишет главы и проверяет, не определено. Э5 («придумай историю на 10 минут») этот путь требует |
| адаптация под короткое внимание | нужен, как режим `story-fix --compress` | S-11 потерян. Диагноз уже покрыт тремя аудитами, не хватает преобразования «сжать до N минут / свести в одну сессию» |
| редактура текста реплик | нужна, в `story-voice` | длина, одна мысль, повторы, род игрока, сшивка — сейчас C-34 у `pace`, C-14 у `choices`, C-46 у `pace`, остальное ничьё |
| ревью плана до написания | есть частично | `plan-check.mjs` проверяет разметку, но аудиторы волны A умеют только ink. Нужен режим `story-review --plan`: по скелету проверить ставку в стволе, распределитель финалов, расписание пауз |
| сопровождение правок между версиями | нужен (`story-release` + `story:diff`) | нет ни сравнения метрик между тегами, ни проверки совместимости сохранений, ни журнала изменений истории |

### 2. Автоподхват

- **Нереалистично в заявленном виде.** Описание скилла — единственное, что модель видит до загрузки.
  Если описание обрезано бюджетом (в этой сессии такое уже есть у чужих плагинов), скилла для
  автоподхвата нет. Агенты подхватываются ещё хуже: главная модель чаще делает работу сама, чем
  делегирует.
- **Конфликты фраз:**
  - «проверь главу» подходит к `story-review`, `story-pace`, `story-auditor`, `chapter-write`
    (`checklist.md`), `story-playtest`;
  - «понятно ли начало» — к `story-opening` и `cold-reader`;
  - «почини» — к `story-fix` и `story-fixer`;
  - «придумай историю» — к `story-core` и `story-architect`;
  - «что подумает игрок» — к `cold-reader` и `story-playtest`.
- **Как развести:**
  1. Пользовательские фразы — только у скиллов. В описании агента: «вызывается только из скиллов
     X, Y, не по просьбе пользователя».
  2. Два явных входа вместо маршрутизатора: `story-review` ловит размытое «посмотри историю / что не так»,
     `story-new` — «придумай / есть идея». Узкие скиллы описываются симптомом («игрок не понимает, кто
     пишет», «кнопки ничего не меняют»), а не темой.
  3. Таблица «симптом → скилл» на 15–20 строк в `CLAUDE.md`. Она загружается в каждый разговор и
     надёжнее описаний.
  4. Отдельный скилл-маршрутизатор не нужен. Это лишний шаг, и он сам конкурирует за бюджет. Его роль
     играют два входа и таблица.
  5. Набор фраз для проверки срабатывания (`docs/lab/triggers.json`: фраза → ожидаемый скилл /
     «ничего») прогоняется при каждой правке описаний через `claude -p` с разбором вызовов Skill
     из потокового вывода.
- **Внутренние скиллы** (`story-continuity`, `story-mystery` при вызове из ревью) пометить так, чтобы
  они не занимали листинг, если T-00 подтвердит такое поле (`disable-model-invocation` или аналог).
  Пользовательские оставить видимыми.

### 3. Контракты

- **150 строк на `SKILL.md`** — нормальный потолок, но мерить надо не то. Главная метрика — длина
  `description`: от неё зависит срабатывание. Нужен жёсткий лимит знаков, не «до 3 строк». Тело лучше
  держать на 60–100 строках: алгоритм, развилки, формат. 150 строк при 13+ скиллах — это ещё и
  стоимость каждой загрузки.
- **Ссылки на свод.** Контракт велит писать в references «правила и пороги с их ID» и «выжимку своими
  словами», то есть третий пересказ (книги → свод → references). **Вместо этого:**
  - в references — только то, чего нет в своде: развилки решений, примеры ink, антипримеры (с
    оговоркой из «Главного», п. 1);
  - правило подтягивается по ID командой `story:rule R-61` (печатает текст из `rules.md`), а не
    копией;
  - «Источники:» генерируются скриптом из ссылок на R/C и проверяются на существование, как в
    `REVIEW.md`.
- **«Одна тема — один владелец»** — правильно, но без ограничения глубины ведёт к цепочкам:
  `chapter-write/buttons.md` → `story-choices/buttons.md` → `structures.md` → свод → книга. Правило:
  reference может ссылаться на свод (ID) и на reference другого скилла **на один уровень**, без
  транзитивных ссылок. Владение темой зафиксировать в таблице `docs/playbook/owners.md` (тема → скилл
  → файл). Сейчас владение размазано по колонкам «знания», и пересечения (п. 1) это доказывают.
- **«Никакой привязки к конкретным историям»** противоречит «антипримерам из наших историй с именами
  узлов». Антипримеры привязывают скилл к трём историям и устаревают после первой же правки узла.
  Хранить их надо в `docs/lab/cases/`, а не в скиллах, и не показывать скиллу на проверочной истории.
- **Формат находки** `флаг · узел · симптом · правка` — добавить уверенность (замер / модель / нужен
  человек) и ID проверки. Без этого не отличить посчитанное от выдуманного, а `skills.md` S-00 сам
  требует помечать «нужен живой тест».

### 4. Агенты

| агент | вердикт | почему |
|---|---|---|
| `story-architect` | **убрать** | создание — диалог с одобрениями (ядро, состав, план). Субагент возвращает результат один раз и не может спросить автора посреди работы. Это скиллы в главной сессии |
| `chapter-writer` | оставить | ограниченная задача с большим выходом: глава по одобренному плану. Агент держит контекст главной сессии чистым. Но только писать: проверки после него запускает главная сессия |
| `story-auditor` | оставить, один с линзами | одна линза = один скилл, агент — только «прогнать скилл X изолированно, только чтение». Разные агенты на каждую линзу размножили бы файлы без выигрыша. Если T-00 подтвердит запуск скилла в отдельном контексте (`context: fork` или аналог), агент не нужен вообще |
| `cold-reader` | оставить, обязательно | единственный агент, где изоляция — суть |
| `story-fixer` | **убрать** | правки по одобрению идут в главной сессии. Параллельные исправители над одним JSON-файлом с ink в одной строке подерутся за файл. Проверку после правки делает хук, а не агент |
| `story-librarian` | **убрать** | `story-kb` в главной сессии + встроенный Explore для поиска по 6 МБ базы. Отдельный агент с Read/Grep повторяет Explore |

- **`model: opus` у всех** — дорого и для холодного читателя вредно. Читатель той же модели, что и
  автор текста, разделяет его предпосылки: модель пишет текст, который проходит её же проверку. Для
  `cold-reader` нужна другая модель (меньше или другого семейства), а для устойчивости — две.
- **Изоляция `cold-reader`.**
  - Поле `tools` задаёт имена инструментов, а не пути: «Read только выданного файла» так не сделать.
  - Плюс субагент, скорее всего, получает `CLAUDE.md` проекта и память (проверить в T-00): там
    названия и описания историй.
  - **Решение:** `tools` пустой, фрагмент переписки — прямо в промпте. Фрагмент режет
    `story:trace --visible --until <узел>`.
  - Надёжнее — вызов вне проекта: скрипт `story:cold-read` через `claude -p` из пустого каталога,
    без инструментов, с системным промптом протокола, или через API.
  - Проверка изоляции — контрольный вопрос «назови имя виновника / последний узел». Читатель не должен
    знать ответа.
- **Кто оркестрирует** — скилл `story-review` в главной сессии: параллельно запускает `story-auditor` по
  линзам и `cold-reader` по режимам, сводит находки. Агенты не вызывают агентов и не вызывают
  `story-review`.

### 5. Фаза 0 и скрипты

**Не посчитано командами:**
- проверки C-NN (`story:lint`) — см. «Главное», п. 2;
- финалы по узлам K-04 (в плане спрятаны в `endings.mjs` скилла, хотя C-40 из первой волны их требует);
- `story:diff <тег> <тег>` — метрики до и после (без него Э3 и Э4 считаются руками);
- `story:pack/unpack`;
- `story:rule`;
- реальное время против `minutes` карточки (C-31 есть в своде, но не в командах);
- время чтения: сессия в минутах при скорости чтения, а не только `#delay` и набор.

**Забыто:**
- **журнал выборов K-05** — кнопка в `DebugSheet`, логика в `engine`. Это изменение поведения чата:
  по `CLAUDE.md` нужна правка реестра (фича `debug`) в том же коммите;
- **персоны:** в плане 4, в `skills.md` K-01 — 6 (`last` и `refuse` выпали). Нужны ещё стратегии «всем
  доверяю / всех проверяю» (`choiceofgames-design:чек-лист §4`) и **«отвлечённый»** персонаж. Он
  уходит на каждой паузе ≥ 30m и возвращается к пачке непрочитанных: что он видит одним экраном до
  кнопки. Это прямой замер главной особенности аудитории. Бот должен падать и на затишье, а не только
  на тупике (`narrative-testing:LESSON-02`);
- **импорт состояния:** `story:trace --from-save <файл>` (сохранение или журнал тестера) и
  `--start ch7 --set ellie_trust=2`. Без этого проверка главы 9 «Чужого голоса» — каждый раз прогон
  всех восьми предыдущих, а баг тестера не воспроизвести;
- **проверка разметки:** неизвестная метка, `at:` на несуществующий узел, `// ось:` на переменную без
  `VAR`, метка, оставшаяся после удаления строки. Без валидатора разметка гниёт молча;
- **одно определение узла.** `check:story` по «Чужому голосу» говорит «узлов посещено 166 из 166»,
  `graph` — «узлов 165». Два разбора уже расходятся. T-01 должен закончиться одной цифрой, и снимок Э1
  без этого не имеет смысла;
- **хук вместо дисциплины:** PostToolUse на правку `src/stories/**` запускает `check:story` и
  `story:lint`. Правило «после правки — `check:story`» в тексте каждого скилла модель будет иногда
  пропускать, хук — нет;
- **орфография.** Шесть списков QA в S-10 требуют «прогнать проверку орфографии». Это внешний словарь,
  а `CLAUDE.md` запрещает лишние зависимости. Решить заранее: devDependency в `scripts/` (не в бандл)
  или проверка моделью.

**Разметка D-01 тяжела и не согласована** — 10 обязательных полей шапки плюс около 15 меток.
- **Автор её не будет поддерживать:** у истории она устаревает с каждой правкой текста, а у старых
  историй уже есть свои шапки комментариями (у THE NUMBER 69 строк `//`: «Кто есть кто», план глав).
  D-01 их не поглощает, а добавляет параллельную схему.
- **Решение:**
  - обязательны 4 поля (логлайн, ставка со сроком, вопрос, оси);
  - остальное ставит скилл диффом комментариев по запросу;
  - где можно — соглашение об именах вместо комментариев (`clue_*` уже используется в C-54,
    `fin_*` — в финалах);
  - метка `// намеренно:` обязательна: без неё нечем гасить ложные срабатывания, а в T-03 её нет.

  Поддерживает разметку скилл, который её читает, а валидатор ловит рассинхрон.

### 6. Эксперименты

- **Э1** — нужен, но после единого определения узла и `story:lint`, иначе снимок нечем сравнивать.
- **Э2** — переделать. Утечка эталона описана в «Главном», п. 1. Дополнительно:
  - топ-10 — это **правки**, а не находки, и 6 из 10 — по одной истории (`chuzhoy-golos`);
  - выборка в 10 пунктов по одной истории статистически ничего не калибрует;
  - «большую часть» в критериях (строка 185) не измеряется.

  **Мерить:**
  - полноту по всем 28 находкам по совпадению узла;
  - точность по отметкам автора;
  - полноту на мутациях: 10–15 внесённых дефектов в чистую копию THE NUMBER (убрать ставку из
    ствола, сделать переменную мёртвой, вставить монолог на 15 реплик, эпилог из 12 сообщений с
    часовыми паузами, контакт с одной репликой);
  - устойчивость: два прогона ревью, пересечение находок.
- **Э3** — «метрики до и после» — закон Гудхарта: исправитель чинит ровно то, что меряет проверка.
  Нужны **отложенные** метрики, которых `story-fix` не видит, и 3–5 живых людей хотя бы на главу 1.
  Это дёшево: сравнение «до / после», один проход без `?fast=1`.
- **Э4** — переписать «Слепое пятно» с нуля, когда оригинал лежит рядом в репозитории: генерация
  подсмотрит. Делать в worktree без `src/stories/slepoe-pyatno.json`. Полезнее и дешевле — новая
  10-минутная история из одной фразы (настоящий сценарий использования). Э4 в нынешнем виде можно
  отложить.
- **Э5** — срабатывание проверяется слишком поздно, после всех волн. Тест фраз должен идти с волны A,
  а Э5 — проверять конвейер `story-new` целиком.
- **«Скучно» и «непонятно» без людей.**
  - **«Непонятно»** проверяется частично: холодный читатель с ключом ответа из шапки (кто, что
    случилось, срок, кто ты) — это тест на понимание с правильным ответом, а не мнение.
  - **«Скучно»** без людей не измеряется — только косвенные признаки: серии без кнопки, затишье,
    микросессии, повторы, ответ «всё равно» в режиме `next`. План должен это сказать прямо и не ставить
    «улучшили оценку холодного читателя по скуке» критерием готовности.
- **Пороги подгоняются под эталон**, раз калибровка «расхождения порогов → правка references» идёт на
  тех же историях, где меряем. Правило: порог меняется только с записью в журнале «на какой истории,
  почему», и после смены проверяется на отложенной истории и мутациях.
- **Добавить метрики:**
  - стоимость прогона (токены, минуты) на скилл и на ревью;
  - доля находок с замером против находок модели;
  - время автора на разбор отчёта;
  - процент принятых правок;
  - регрессии (`check:story`, `test:e2e`, совместимость сохранений);
  - доля прогонов, где «отвлечённый» видит после паузы больше 5 сообщений до кнопки.

### 7. Порядок

- **«Сначала диагноз, потом создание» — верно:** на трёх историях польза видна сразу, а критерии
  диагноза становятся критериями готовности для создания.
- **Неверно, что волна A собирает восемь скиллов параллельно до первой обратной связи.** Восемь
  сборщиков `claude -p` по одному шаблону повторят одну и ту же ошибку восемь раз. **Вместо этого —
  вертикальный срез первым:**
  1. `story-choices`, главная боль;
  2. `story:lint` с его проверками;
  3. формат находки;
  4. один приём ремонта;
  5. тест срабатывания;
  6. мини-эксперимент на одной истории.

  Шаблоны правятся по итогам, затем остальные скиллы — параллельно.
- **Ремонт отдельной волной B** противоречит `skills.md` («приёмы пишут вместе с первым аудитом,
  которому они нужны»). Автор узнает о находке и долго не сможет её починить скиллом. Приём F-NN
  собирается вместе со скиллом, который его предлагает. `story-fix` — только общая безопасность
  правок и режим сжатия.
- **Узкое место** — последовательная цепочка T-01 → T-02 → T-03. Параллелить можно:
  - T-00 и T-05 (шаблоны) — сразу, они не зависят от библиотеки, но в плане T-05 стоит последним
    (строка 193);
  - `story:lint` по группам проверок — после T-01;
  - набор фраз для теста срабатывания — сразу.
- **Риск переделок.** D-01 (T-03, сложность L по C-53) проектируется до того, как хоть один скилл
  показал, какие метки реально нужны. Делать минимальные 4 поля в фазе 0, остальное — по требованию
  скиллов.
- **Эксперименты не на `master`.** Пуш в `master` деплоит Pages (`CLAUDE.md`). Тег `stories-v1`
  защищает от потери, но не от выкладки перекопанных историй игрокам. Эксперименты — в ветках или
  worktree.

### 9. Что забыли

- **Тестирование самих скиллов как регрессия:**
  - золотые выходы на мутантах;
  - набор фраз срабатывания;
  - CI-скрипт `npm run skills:test`, который гоняется при правке скилла.

  Пункт «ревьюер скилла дал готово» — это мнение модели, а не тест.
- **Версии.**
  - Поле `version` в историях есть, но движок его не читает при восстановлении.
  - Нужны: правило «правка ink → +1 версия», журнал изменений истории, решение для старых сохранений
    (сброс с предупреждением или запрет менять узлы до текущей позиции игрока).
  - Скиллам тоже нужна версия: какой версией скилла сделан отчёт.
- **Стоимость.** По грубой оценке, ink «Чужого голоса» — 99 тыс. знаков, порядка 30 тыс. токенов. Ревью
  — 6–8 аудиторов, каждый читает ink, вывод команд и свои references: при 60–100 тыс. токенов на
  аудитора это 0,5–0,8 млн токенов на одно ревью одной истории на Opus. Э2 с итерациями калибровки —
  несколько миллионов. Бюджета и метрики стоимости в плане нет. Решение: `--quick`, кэш вывода команд
  в `docs/lab/cache/`, аудитор читает только свои узлы по выводу `story:lint`, а не весь ink.
- **Отказоустойчивость.** Что делает скилл, если команда упала, ink не компилируется или разметки нет?
  Нужно правило: скилл не подменяет замер оценкой «на глаз», а пишет «нет данных: <команда> упала» (в
  `skills.md` это декларировано, в контракте плана — нет).
- **Ручной режим без ИИ.** `story:lint`, `story:trace`, `graph` и чек-листы из `rules.md` «Короткая
  версия» должны быть полезны автору без Claude. Тогда план выдержит смену инструмента, а автор
  научится видеть проблему сам. Отчёт `story:lint` должен читаться человеком.
- **Обучение автора** — см. «Главное», п. 7.
- **Права и этика контента.** Тяжёлые темы в `synopsis` проверяет S-10 (`skills.md`), в плане это ушло.
  Перенести в `story-release`.
- **Данные реальных игроков.** Для платного продукта нужна аналитика: где бросают, сколько
  возвращается после паузы. Это единственный честный замер «скучно». План полностью опирается на
  бота и модель. Хотя бы записать как фичу `planned` (анонимный журнал прохождения, по согласию).

### 10. Будущее

- **Десятки историй.** Бюджет листинга от числа историй не зависит, это хорошо: скиллы не привязаны к
  историям. Плохо — антипримеры и `cases.md` внутри скиллов. При десятке историй они либо устареют,
  либо раздуют references. Кейсы — в `docs/lab/cases/`.
- **Вселенная.** Не закрыта, но и не подготовлена:
  - прогресс по `relay:<storyId>`, межисторического состояния нет;
  - D-01 без полей мира;
  - канон персонажей не хранится нигде, кроме ink.

  Минимум сейчас: `series` уже есть в формате — завести `docs/worlds/<series>/` (персонажи, хронология,
  факты), а `story-continuity` пусть проверяет и его. Фичу движка «флаги, видимые другой истории
  серии» — в реестр как `planned`.
- **Платные дополнения.** Точка оплаты — стык глав. Значит, `story:sessions` и `story-release` должны
  показывать, где стоит граница и что на ней обещано. Этика (R-114, R-115) — обязательный гейт выпуска.
  Сейчас платность не учтена нигде.
- **Другие авторы.** Ломается на трёх вещах:
  - тяжёлая разметка D-01;
  - ink в JSON-строке;
  - скиллы, которые предполагают знание свода.

  Нужны `story:pack/unpack`, минимальная шапка и README «как писать историю» без Claude.

   дадут оба файла, получит две разные спецификации.
2. **T-03 (строка 88): «реестр возможностей не меняется»** ↔ `checks.md` C-53: «Разметку надо внести в
   `docs/capabilities.json` и PROMPT» ↔ `skills.md` D-01, «Готово»: «раздел о шапке в README и

3. **T-03, поля разметки.**

5. **«Одна тема — один владелец» (раздел 1 плана) ↔ таблица волны A:** C-37 у `story-pace` и

7. **«Никакой привязки к конкретным историям» (раздел 1) ↔ «антипримеры из наших историй, с именами
   узлов» (тот же раздел) и `cases.md` у `story-opening`.**
8. **`story-auditor` «вызывает `story-review`» (строка 143) ↔ `story-review` «запускает аудиторов»

9. **`cold-reader`: «Read (только выданный файл)» (строка 144)** — поле `tools` так не ограничивается.
10. **`story:cast`: «Прототип: подсчёт из обсуждения персонажей» (строка 82)** — в репозитории такого

11. **`skills.md`: приёмы F-NN «пишут вместе с первым аудитом»** ↔ план: отдельная волна B после всех
    аудитов.
12. **Счёт узлов:** `check:story` — «166 из 166» для `chuzhoy-golos`, `graph` — «узлов 165».
    Постановка задачи тоже опирается на 165.
13. **План ↔ `CLAUDE.md`.**
    - Пуш в `master` = деплой, а план перекапывает истории без ветки.
    - Изменение поведения чата требует правки реестра в том же коммите, а журнал K-05 (если его
      вернуть) — это изменение `DebugSheet`.
    - «Никаких зависимостей сверх необходимых» против проверки орфографии в S-10.
    - Таблица команд и «Проверка перед коммитом» в `CLAUDE.md` должны получить `story:*`. План
      упоминает только «`CLAUDE.md` знает про агентов и скиллы».
14. **Карточки ↔ реальное время.** `chuzhoy-golos`: `minutes` ≈ 90, реальные паузы — 166–185 ч.

    нарушают собственное правило свода, а в плане у этого нет владельца.
15. **`engine.ts` `restore()`** проверяет только формат сохранения (`v` 1 или 2) и `storyId`, но не
    версию сценария. Это противоречит допущению плана, что истории можно свободно перекапывать.

## Что оставить как есть

- **Разделение «команда считает, модель судит».** Каждое число — из команды. Это единственная защита
  от уверенных выдуманных метрик.
- **Общий `scripts/lib/` и перевод `check-story` и `story-graph` на него.** Расхождение 165/166 узлов
  показывает, что это нужно было ещё вчера.
- **Формат находки с именем узла** и правило «сначала непонятное, потом скучное». Это проверяемо и
  сортируемо.
- **«Только теги `ready`» и сверка реестра со сборкой промпта.** Скиллы не могут разъехаться с
  движком.
- **Один аудитор с линзами вместо агента на каждую теорию.** `skills.md` §7 верно объясняет: шесть
  теорий дают противоречивые правки.
- **Холодный читатель с режимами и зачётом**, особенно `return` и `button`. Это лучшее приближение к
  «понятно ли» без людей, если починить изоляцию.
- **Журнал экспериментов** с полями «совпало / пропущено / ложное / какие пороги поменяли». Он
  нужен, только с отложенной выборкой.
- **Тег `stories-v1`** как точка сравнения.

## Ответы автора (24.10.2026)

1. **Реальное время.** Задумано два режима игры. В «реальном времени» персонаж уходит («разожгу костёр, отпишу») и пишет через настоящие часы — это любимый режим автора. В режиме «по клику» ответ приходит сразу, для тех, кто не хочет ждать (так попросили двое коллег). Неделя у «Чужого голоса» — следствие сценария под реальное время. Сейчас «по клику» есть только как отладочный `?fast=1`.
2. **Гибрид.** Автор накидывает идеи и грумит, а сценарий и сюжет по очереди прорабатывает, тестирует, правит, оценивает и переписывает ИИ.
3. **Живые тестеры:** автор и 2–3 человека.
4. **Сохранения не важны:** истории можно переписать с нуля.
5. **Платность не решена.** Идея: 1–2 главы бесплатно, дальше покупка. Истории не должны открываться только через прохождение другой истории: связи гибкие, без замков.
6. **Время действия** — настоящее или будущее, сюжеты можно брать из книг и переосмыслять.
7. **Отдельные `.ink`-файлы — да.** Один JSON был нужен для быстрой загрузки, деплоя на Pages и теста на телефоне.
8. **Шапка** — вопрос уточняется.
9. **Бюджета нет:** главное — качество и результат через тесты и симуляции.
10. **Другие авторы** будут работать по тому же процессу: идеи → груминг → фокус на одной → финализация → пара глав для теста.
11. **Лишние плагины и MCP** в проекте можно отключить, оставить только то, что помогает работать здесь.

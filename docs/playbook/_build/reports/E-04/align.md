# E-04 — сверка с замыслом

Вердикт: drift-minor

## Исправил сам
- `README.md`, комментарий у поля `revision` в `meta.json`: было «+1 на каждую выпущенную правку текста», а реестр (`docs/capabilities.json`, фича `revision`) говорит «поднимать только когда правка ломает сохранения». После E-04 подъём ревизии стирает прогресс игроков, поэтому старая формулировка вела автора к лишним сбросам. Теперь README совпадает с реестром и закрывает просьбу из `requests.md`: сброс с предупреждением, нет поля — 1.

## Дрейф (если есть)
Крупного нет. Задача в рамках своего раздела (§11, E-04) и своих путей (`src/**`, реестр, `CLAUDE.md`, `e2e/**`). Отступления от плана записаны в `build.md` («Решения»).

Перезапуск по ревизии — не способ сменить режим втихую: на экране истории игрок выбирает режим заново, потому что старой игры нет. Это согласуется с замыслом.

## Риски для следующих задач
- **E-05** (`free_chapters`, тоже `StoryScreen`/`StoryTile`/`progress.ts`). Экран истории теперь различает `saved` (сырое сохранение) и `progress` (`null` при устаревшей ревизии). Закрытые главы нужно считать по `progress`, а не по `saved`, иначе устаревшее сохранение покажет «продолжение платное» вместо начала.
- `choiceLog.ts` пишет `revision: story.revision ?? null`, а не `revisionOf(story)`. Это противоречит правилу «нет поля — 1»: журнал истории без поля приходит с `null`. Код старый, до E-04, и `story:trace --from-save` поле пока не читает. Если сверку ревизии журнала добавят в `story:trace`, нужно привести к `revisionOf`.
- Замечание ревью: `useState` для `outdated` в `useGame` берётся один раз. Это сработает, если появится смена ревизии без размонтирования, например горячая перезагрузка файла истории в игре.

# Формат находки и источники: замер, модель, человек

Одна строка — одна находка. Её пишут все диагностические скиллы и агент `story-auditor`, её читает
`merge-findings.mjs`, её видит автор в отчёте. Формат общий для всего цикла (`build-plan.md` §4, кластер TH-28):

```
P1 · непонятно · <узел> · симптом · правка (F-NN) · [C-NN · замер|модель|человек · уверенность]
```

## Поля по порядку

| поле | что писать | чего не писать |
|---|---|---|
| `P1`…`P3` | приоритет по [priority.md](priority.md) | «важно», «критично» словами |
| тип | один из пяти: баг · непонятно · нестыковка · не верю · скучно; «(кандидат)», если нет человека | «плохо», «слабо», «можно лучше» |
| узел | id узла ink; список через запятую; глава — «(гл. N)»; у холодного читателя — «цитата начала сообщения» | номер строки файла, «где-то в середине» |
| симптом | что почувствует игрок и где именно, одной-двумя фразами | рецепт вместо симптома |
| правка | приём `F-NN` владельца или имя приёма из его references; нет приёма — «→ <скилл>» | готовую реплику: варианты строит `story-fix` после одобрения |
| скобки | проверка `C-NN` (если есть), источник, уверенность (высокая / средняя / низкая); у панели — «симуляция» | число без ключа `thresholds.json` |

Узел — третьим полем, приём — в поле правки: в живых ответах поля плавали, и сводка теряла место находки.
`merge-findings.mjs` разбор делает терпимым (узлы списком, «правка:», «(гл. 2)»), но порядок полей — обязателен.

## Три источника

- **замер** — число из команды: `story:lint`, `story:*`, скрипт линзы. Сам по себе не находка: его сверяет
  с узлом и правилом аудитор (LOCAL-04). Неподтверждённая строка идёт в приложение «замер без сверки».
- **модель** — суждение там, где замер молчит: тон, мотив, смысл кнопки. Всегда с уверенностью. «Скучно»,
  «непонятно», «не верю» от модели без человека — «кандидат» (`build-plan.md` §13).
- **человек** — тестер или автор. В скобках — сколько людей: «человек · 2 из 3». Его симптом реален, рецепт —
  нет ([conflicts.md](conflicts.md)).

Холодный читатель (`story:cold-read`) — модель с пометкой «симуляция»: он сильнее модели-аудитора на
«непонятно» (не знает истории), но не заменяет человека на «скучно» и «не верю» (A-07: только Opus,
разброс — профилями, а не второй моделью).

## Разделы ответа линзы

Агент `story-auditor` отдаёт, кроме находок, три раздела — `merge-findings.mjs` читает их тоже:
- **ложные** — `C-NN · узел · почему не находка` или `намеренно: C-NN · узел`: строка `story:lint` не идёт в
  отчёт, а в приложении — предложение `// намеренно: C-NN причина` над узлом;
- **нет данных** — какая команда упала и что вывела; число вместо неё не придумывается;
- **вне линзы** — `story-<скилл> · узел · одна строка`: замечено на чужой территории, разбирает владелец.

## narrative-testing:P-02 · Два прохода: поломки отдельно, впечатление отдельно

Сначала проход «работает по замыслу»: тупики, неизвестные теги, недостижимые узлы, мёртвые переменные —
это служебные проверки бота C-52, разметка C-53, недостижимое C-15, мёртвая переменная C-01. Потом проход
«замысел хорош»: понятно ли, интересно ли, веришь ли игроку, который на автора не похож. Если смешать,
внимание тратится на опечатки и тупики, а дыры сюжета остаются; и наоборот — чистый отчёт бота автор
принимает за «история хорошая». Поэтому в отчёте два раздела: «Поломки» и «По главам» (впечатление), и
второй не бывает пустым, пока ревью не прошли линзы и холодный читатель.
- **Когда не работает.** История из пяти сообщений: оба прохода — один короткий прогон, разделять нечего,
  но раздел «Поломки» всё равно пишется первым. Скелет (`--plan`): впечатление по скелету — только от
  читателя (Б-7), линзы текста не запускаются.
- **Масштаб.** На 5 сообщениях поломки — одна строка «нет»; на 50 и больше поломки занимают первый экран,
  и без раздела «впечатление» автор не дочитает до сюжета.
- basis: checked (разделение «соответствует спецификации» и «спецификация хороша» в обсуждении тестирования IF).

## mckee-story:LESSON-12 · У суждения есть число или проверка

Критика книги практиком: многие советы там вида «соли по вкусу» — слишком много плохо и слишком мало плохо, а эвристики и порога нет. Такой совет автору бесполезен. Всё, что ревью
берёт из теории, получает либо проверку (`C-NN` с ключом порога в `thresholds.json`), либо явную пометку
«модель · уверенность». Находка без того и другого в отчёт не идёт: её нельзя ни перепроверить, ни
закрыть. Поэтому линзы теорий в [lenses.md](lenses.md) — вопросы, каждый с проверкой, которая даёт число
(C-38 для пропорций глав, C-04 для дальности отклика, C-08 для цены до кнопки).
- **Когда не работает.** «Не верю» и голос: числа там косвенные (C-44 даёт профиль, а не вердикт). Тогда —
  модель с уверенностью и, если можно, человек.
- basis: secondary (критика книги практиком) · наше применение к формату находки.

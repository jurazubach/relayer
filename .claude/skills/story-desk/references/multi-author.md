# Несколько авторов в одной истории (Б-6)

В relayer у истории почти всегда больше одного пишущего: автор, ИИ-генератор (`chapter-writer`), ревьюер,
иногда второй человек. Структура, которую держит в голове один, ломается при первой правке чужими руками.
`story-desk` отвечает за три вещи: кто ведёт какую главу, как главы лежат в git, и что решения подписаны.

## Правила

1. **Кто ведёт главу — в `STATUS.md`,** раздел «Кто что пишет»: `- глава 4 — Даша, черновик`,
   `- главы 5–7 — chapter-writer`. Проверка: `node ${CLAUDE_SKILL_DIR}/scripts/story-status.mjs --owners --story <id>`
   (глава → кто ведёт → последний автор в git) и `--check` (у какой главы не записано).
2. **Глава — отдельный файл через `INCLUDE`** (`src/stories/<id>/chNN.ink`): два человека правят разные
   файлы и не конфликтуют в git. Раскладку проверяет `npm run story:pack -- --check`. Общие функции и узлы —
   в `common.ink`, его правит тот, кто ведёт историю.
3. **Решения подписаны:** поле «кто» у каждого D-NN — имя, а не «мы». Чужое решение не правится, а
   заменяется новым (`--replaces`).
4. **Стиль второго автора** — `docs/authors/<имя>/style.md` поверх общего `docs/style.md`. Снимает и
   применяет его `story-voice` (`author-style.md`, `style-diff.mjs`); `story-desk` только записывает, что такой
   файл есть, в «Кто что пишет».
5. **Легенда структуры — командами, а не памятью:** что пишет и читает каждая переменная — `npm run story:vars`,
   какой финал от чего — `npm run story:endings`, карта — `npm run graph`, правда мира — `facts.md`. Второму
   автору даётся их вывод, а не пересказ.

### bateman-game-writing:P-08 · структура, которую понимает не только автор

Бейтман признал многониточную структуру Discworld Noir неудачей: в частности, её понимал только он сам, и для
команды это был риск. Механизм: без записи о том, какая переменная что открывает, правка одной главы молча
ломает другую — особенно когда главы пишет генератор или второй автор. Источник предлагал комментарий над
каждой `VAR` (где ставится, где читается, на какой финал влияет); у нас эта часть заменена решением A-06:
связи считает `npm run story:vars` (запись → чтение, мёртвые и невидимые переменные), а финалы —
`npm run story:endings`. Легенда не устаревает, потому что она вычисляется.
**Когда не работает:** вычисленная легенда показывает связи, но не намерение — зачем переменная и какую нить
ведёт. Намерение живёт в плане (`plans/plan-vN.md`) и в `facts.md`; если второй автор правит главу без плана,
команда не спасёт. **Масштаб:** на 5 сообщений с одной переменной легенда не нужна; на 50 и больше с
несколькими пишущими — обязательна до передачи главы.

### bateman-game-writing:P-08#нюанс · знать фон целиком, вести биографии для команды

Дополнение второго прохода: Rhianna Pratchett советует знать фон мира целиком, даже если игрок увидит только
верхушку айсберга, и вести биографии персонажей для других участников команды. Для нас это «лист мира» не для
игрока, а для генератора и второго автора: `facts.md` (кто что знает, хронология) и служебные поля `voice` и
`arc` в `characters` файла `meta.json` — экран истории их не показывает. `story-desk` проверяет при передаче
главы, что лист есть и новее ядра (`stale-check.mjs`, п. 2). **Когда не работает:** биография, которую никто
не читает при письме, — анкета ради полей; в пакет главы (`chapter-context`) идёт только то, что глава
использует.

### bateman-game-writing:LESSON-03 · рисуй структуру так, чтобы её читал не только автор

Discworld Noir: нити-виньетки шли параллельно и открывались в разное время; игроки чувствовали больше
свободы, чем было, но структуру понимал только Бейтман, и уход одного человека остановил бы проект. Вывод
доклада — рисовать граф хребта, особенно где он ветвится, и группировать повествование в акты или нити, чтобы
схему читали остальные. У нас граф строится сам (`npm run graph`), но граф не объясняет намерение. Проверка
передачи главы второму автору: по выводу `story:vars`, `story:endings` и карте он отвечает, какой финал
получит игрок с заданным набором переменных. Не ответил — легенды не хватает, дописываем план, а не
комментарии в ink.

### bateman-game-writing:GREEN-06 · у каждой переменной известно, где ставится и где читается

Зелёный флаг источника: у каждого `VAR` в шапке комментарий — где ставится, где читается, на какой финал
влияет; правка одной главы тогда не ломает молча другую, а генератор видит связи. Цель в силе, способ заменён
(A-06, R-39): комментарии над `VAR` не заводим, связи показывает `npm run story:vars`. Зелёный флаг у нас:
`story:vars` не находит переменных «мёртвая» и «невидимая», и у каждой главы, которую ведёт не автор истории,
есть план с переменными, которые глава пишет и читает. Неиспользуемую переменную удаляют вместе с кнопкой,
а не оставляют «на потом».

## Как передать главу второму автору

1. `story-status.mjs --owners` — у главы записан ведущий; запись в «Кто что пишет».
2. Пакет: план главы, `facts.md`, вывод `story:vars` и `story:endings`, концы прошлой главы по путям
   (`chapter-context` у `chapter-write`).
3. Стиль: общий `docs/style.md`, поверх — `docs/authors/<имя>/style.md`, если есть.
4. Решение D-NN «главу N ведёт <имя>» с подписью того, кто передал.
5. По возвращении главы — быстрый хук на правку, полный прогон главы, `stale-check.mjs`.

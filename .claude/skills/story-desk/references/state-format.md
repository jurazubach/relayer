# Состояние истории: `docs/stories/<id>/`

Состояние работы над историей живёт в репозитории, а не в памяти сессии (`build-plan.md` §1, §7). Его читает
каждый скилл первым шагом, его печатает хук `SessionStart` (`npm run story:status`). Здесь — состав папки,
шаги, кто какой файл пишет и как по ним понять, где мы.

## Состав папки

```
docs/stories/<id>/
  STATUS.md          шаг, активная ли, кто ведёт, ядро (D-NN), план (путь), обновлено; открытые вопросы,
                     кто что пишет, что устарело
  decisions.md       журнал D-NN — формат в decisions-log.md
  ideas.md           банк идей I-NN — формат в ideas-bank.md
  plans/plan-vN.md   версии плана; первая строка «core: D-NN» — на каком ядре построен
  plans/skeleton.ink скелет всей истории («// core: D-NN» в первых строках)
  facts.md           правда мира: кто что знает, хронология (ведёт story-continuity)
  reviews/<дата>-<скилл>.md  отчёты ревью и диагностических скиллов (story-review, story-choices …)
  playtests/wave-N/  комплект и сводка волны теста (story-playtest)
```

Ink истории лежит отдельно, в `src/stories/<id>/` (главы — `chNN.ink` через `INCLUDE`). Папку состояния
заводит `node ${CLAUDE_SKILL_DIR}/scripts/story-status.mjs --init <id>`: шаблон
`scripts/story/templates/STATUS.md` плюс пустые `decisions.md` и `ideas.md`. Уже заведённое не трогает.

## Кто какой файл пишет

| файл | пишет | читает | когда меняется |
|---|---|---|---|
| `STATUS.md` | `story-desk` (шаг, активная, ведущие, «Устарело»); `decision-add.mjs --set-core / --set-plan` | все скиллы первым шагом, хук `SessionStart` | на каждом переходе шага и при смене ядра или плана |
| `decisions.md` | `story-desk` по согласию автора (в конвейере — королевы) | `story-review` (отклонённые находки), `story-fix`, `stale-check.mjs` | каждое решение — новая запись, старые не правятся |
| `ideas.md` | `story-desk` (`idea-park.mjs`) | `story-brainstorm` (банк для новых направлений), `story-branch` | отвергли направление, план, развилку, рецепт тестера |
| `plans/*` | `story-plan`, агент `story-architect` | `chapter-write`, `stale-check.mjs` | новая версия — новый файл, не правка старого |
| `facts.md` | `story-continuity` | `chapter-write` (пакет главы), ревью | глава добавила факт — в том же коммите |
| `reviews/`, `playtests/` | `story-review`, `story-playtest` | `story-fix`, `story-desk` (Б-1) | после каждого прогона |

**Отчёт скилла в `reviews/`.** Файл `reviews/<дата>-<скилл>.md`: шапка (история, ревизия `meta.json`,
коммит), находки строками общего формата, сверка (что ложное и почему), предложенные правки. В `STATUS.md` —
одна строка в «Открытые вопросы»: «ревью <скилла> <дата>: P1 — N, P2 — M, главное — …, отчёт — reviews/…».
Отчёт старше правок глав `stale-check.mjs` показывает в п. 4.

Правило одного места: решение записывается один раз, в `decisions.md`, а в `STATUS.md` стоит только ссылка
на его номер. Если ядро описано и в `STATUS.md`, и в решении, со временем они разойдутся.

## Шаги цикла

Шаг в `STATUS.md` — строго из списка плана §7: `idea`, `directions`, `core`, `plan`, `skeleton`,
`chapters:1-2`, `review`, `fix`, `playtest:wave1`, `chapters:3-N`, `review:full`, `playtest:wave2`, `release`.
Шаг — то, что закрыто последним: `шаг: chapters:3-N` значит «все главы написаны, дальше полное ревью».
Порядок, кто ведёт работу после шага и чем она закрывается — `systems/cycle.md` и
`node ${CLAUDE_SKILL_DIR}/scripts/story-status.mjs --next --story <id>`. Неизвестный шаг `story:status`
помечает «не из списка плана §7», `story-status.mjs --check` даёт ошибку.

## Несколько историй

- Активная — та, где `активная: да`. Если метки нет — по ветке `story/<id>`, иначе правленная последней
  (`scripts/story/core/state.mjs`). Сменить: `story-status.mjs --activate <id>` (снимает метку с остальных).
- Таблица всех — `npm run story:status -- --all`; там же истории каталога без папки состояния.
- Банк идей общий: `idea-park.mjs --list` ищет по всем `ideas.md`.

## Ревизии и откат

- Ревизия сценария — поле `revision` в `meta.json` и тег git `<id>-rN` на коммит выпуска ревизии.
- Сравнить две ревизии — `npm run story:diff -- <id>-r2 <id>-r3`; реплики до и после — `--text`.
- Откат — не правка истории git, а новое решение D-NN «откат к …» с причиной. Журнал помнит, что было.
- Версионирование сохранений и журнал изменений для игроков ведёт `story-release` (`versioning.md`).

### dille-ultimate-guide:SYS-1 · конвейер документов → наши файлы

У Dille и Platten работа сценариста идёт по цепочке документов: pitch (питч) → concept (концепт) →
bible (библия правды мира) → design doc (поток глав) → script (реплики). Выход каждого документа — вход
следующего, и каждый отвечает на вопрос, который иначе всплывёт посреди текста (темы подтверждены, а порядок
и связь «выход = вход» — реконструкция разбора, уверенность средняя). У нас конвейер разложен
по папке истории, а не по комментариям в ink (шапка ink — только 4 строки, ⊘ A-06):

| документ | у нас | кто ведёт |
|---|---|---|
| питч | `tagline`, `synopsis`, обложка в `meta.json` | `story-brainstorm` → `story-release` |
| концепт | ядро: решение D-NN «ядро vN» + шапка ink из 4 строк | `story-core` |
| библия | `facts.md`, `characters` в `meta.json` | `story-continuity`, `story-cast` |
| поток | `plans/plan-vN.md` и `plans/skeleton.ink` | `story-plan` |
| сценарий | `src/stories/<id>/chNN.ink` | `chapter-write` |

**Когда не работает:** если документы пишут один раз и бросают. Библия, которую не правят вместе с ink,
хуже отсутствующей: ревьюер сверяет текст с неверным эталоном. Поэтому документ правится в том же коммите,
что и ink, а смену ядра ловит `stale-check.mjs`. **Масштаб:** история на 5 сообщений обходится без плана —
шаг `plan` сжимается до одной строки скелета; на 50 сообщений и больше нужны все пять звеньев. По шагам,
ошибки понимания и короткая форма — `systems/document-pipeline.md`.

### procedural-storytelling:LESSON-07 · вкладываться в инструменты автора

Emily Short про Versu: инструменты автора (визуализация потока истории, анализ тестовых прогонов, детектор
застрявшей сцены) ускорили производство контента, по её оценке, в разы, и дали больше, чем дал бы новый
движок. Урок для нас: самый дешёвый рост качества — новые проверки и команды, которые считают, а не новые
теги. Поэтому состояние истории читают команды, а не модель на глаз: `npm run story:status` (шаг, ядро, план,
решения), `stale-check.mjs` (что устарело), `story-status.mjs --check` (формат), `idea-park.mjs --list`
(банк). Модель судит по их выводу; если команда упала — «нет данных: <команда>», а не догадка.

**Когда не работает:** инструмент без того, кто им пользуется, — мёртвый код. Команда, которую ни один
скилл не зовёт на своём шаге, не ускоряет ничего; поэтому каждая команда здесь стоит в шаге алгоритма
`SKILL.md`. Оценка ускорения — слова автора инструмента, а не замер (класс C в `lessons.md`).
